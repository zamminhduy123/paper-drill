Scope Diagnosis: Transfer Bottlenecks Across IVN, IoT-IDS, NIDS

The core problem across all three scopes is domain shift : models trained on one network environment (in-vehicle CAN bus, IoT/IIoT traffic, enterprise NIDS) fail catastrophically when deployed on another, even when the abstract attack categories (DoS, flooding, fuzzing) appear semantically similar. The search results confirm this gap is pervasive and under-addressed.

IVN-Specific Bottlenecks

* Author-stated : "The ROAD dataset is highly imbalanced... some classes need to be oversampled. For this reason we employed the SMOTE algorithm... to increase the number of samples of each attack to a fixed value of 100,000" - 1 . Cross-dataset CAN evaluation shows "statistical features provided near-random detection performance with ROC-AUC values as low as 0.0088 (Logistic Regression) and 0.0145 (Fuzzy → RPM) when models were trained on one attack type and evaluated on RPM spoofing attacks" - 6 .

* Inference (model's) : The F1=0.02 on HCRL DoS and F1=0.27 on ROAD cross-ID fuzzing likely stem from a fundamental mismatch: CAN ID is treated as a categorical anchor in residualization schemes, but novel-ID flooding renders that anchor null, and cross-ID fuzzing blurs the decision boundary between "unusual ID" and "attack ID."

* Proposed experiment : Train a CAN ID anomaly detector exclusively on Car-Hacking normal traffic (no attack samples), then evaluate zero-shot on ROAD fuzzing and CAN-ML novel-ID attacks. Measure whether per-ID baseline instability predicts false positives.

IoT-IDS Bottlenecks

* Author-stated : "No single architecture dominates, reflecting the diversity of IoT scenarios and operational constraints. Hybrid and attention-based models generally improve detection effectiveness... but these gains often come at the cost of increased computational overhead" - 3 . "Heavy reliance on benchmark datasets with limited cross-dataset or real-time validation" - 3 .

* Inference (model's) : The triple-model stacking with meta-classifier described in the IoT scope is the canonical example of architectural complexity without deployment feasibility — the meta-classifier's latency is unmeasured on constrained hardware, and the architecture assumes stationary feature distributions that do not hold across IIoT verticals.

* Proposed experiment : Distill a multi-stage model trained on CIC-IoT-2023 into a single lightweight classifier, then evaluate transfer to N-BaIoT and TON_IoT with latency profiling on simulated edge constraints.

NIDS Bottlenecks

* Author-stated : "When trained on UNSW-NB15 and tested on TON_IoT or vice versa, below 40% accuracy. These results reveal a significant generalisation gap in intrusion detection" - 28 . "The field's near-universal omission of FPR, latency, and resource consumption metrics... means that benchmark accuracy rankings do not reliably predict production deployment suitability" - 12 .

* Inference (model's) : The NIDS scope's limitation — "no cross-domain or IVN validation; meta-learner interpretability and feature-space transferability unaddressed" — reflects a broader pattern: NIDS methods optimize for tabular flow features from enterprise traffic, which have no structural correspondence to CAN frames or IoT protocol-specific features.

* Proposed experiment : Map NIDS flow features to IoT-flow features via shared statistical moments (packet inter-arrival variance, byte entropy), train on CIC-IDS-2017 , test zero-shot on CIC-IoT-2023 with feature alignment only.

Concrete Research Splits: Method X from Scope A → Problem Y in Scope B

All proposed splits use only the permitted datasets: Car-Hacking, ROAD, CIC-IoV-2024, CAN-ML, N-BaIoT, TON_IoT, CIC-IoT-2023, CIC-IDS-2017, UNSW-NB15, CIC-DDoS-2019.

Split 1: Statistical Flow Feature Transfer (NIDS → IoT-IDS)

Method X (NIDS) : Statistical flow feature extraction + tree-based ensemble (as in - 23 , where DT achieved 96.25% cross-dataset accuracy TON_IoT → WUSTL-IIoT-2021 on 7 shared features).

Problem Y (IoT-IDS) : Cross-vertical IoT attack detection where labeled target data is scarce.

Component                      Design
Source training                TON_IoT — extract statistical flow features (src/dst port, packet counts, byte counts, duration)
Target evaluation (zero-shot)  CIC-IoT-2023 — map shared semantic features, no retraining
Target evaluation (few-shot)   N-BaIoT — fine-tune on 5% labeled target samples
Baselines                      Random Forest, Decision Tree, Logistic Regression trained natively on target
Primary metric                 Macro-F1 on minority attack classes (not accuracy)


Author-stated support : "Tree-based ensemble models such as Bagging and Stacking show strong generalizability across datasets, whereas LGBM appears to struggle with domain shift" - 23 .

Inference : If semantic feature mapping preserves enough discriminative signal for DoS-like attacks, zero-shot F1 > 0.60 is achievable; fuzzing/spoofing attacks will likely fail without temporal features.

Proposed experiment : 1. Extract 7 shared features from TON_IoT and CIC-IoT-2023. 2. Train RF on TON_IoT binary (benign/attack). 3. Evaluate on CIC-IoT-2023 DDoS, DoS, Mirai subsets. 4. Report per-class F1 and confusion between attack types.

Split 2: Curriculum Learning Transfer (IoT-IDS → IVN)

Method X (IoT-IDS) : The "structured curriculum learning strategy" described in - 31 — first-stage normal traffic training, second-stage scenario simulation, third-stage attack data.

Problem Y (IVN) : Cross-vehicle CAN attack generalization, where different vehicles have different ID mappings and message periodicities.

Component          Design
Source curriculum  Train on CIC-IoV-2024 with three-stage schedule (normal → simulated control modifications → DoS)
Target zero-shot   ROAD — evaluate on Chevrolet Spark, Hyundai Sonata, Kia Soul separately
Target few-shot    CAN-ML — fine-tune with 10% of target vehicle's attack samples
Baselines          Train directly on ROAD target vehicle
Primary metric     Cross-vehicle F1 variance (how stable is performance across vehicles?)


Author-stated support : "The application of the same attack types and setup on three different vehicles makes this dataset unique and enables us to test transfer learning approaches on it, in order to improve the generalizability of the model" - 1 . CIC-IoV-2024 was trained via "a three-part procedure... normal driving data... simulation scenarios based on modifications to GAS, RPM and SPEED... DoS attack data" - 31 .

Inference : Curriculum ordering may help, but CAN ID distributions differ fundamentally across vehicles — the model must learn to ignore ID-specific features unless the curriculum explicitly teaches ID-invariance.

Proposed experiment : 1. Train a CNN-LSTM on CIC-IoV-2024 with the three-stage curriculum. 2. Freeze and evaluate on ROAD vehicle-held-out splits. 3. Ablate curriculum stages to isolate which phase contributes to cross-vehicle transfer. 4. Compare against direct ROAD training with 80/20 split.

Split 3: Residualization Transfer (NIDS → IVN)

Method X (NIDS) : Residual-based anomaly detection where the model predicts expected feature values and flags deviations — conceptually aligned with the residualization mentioned in the IVN scope but not yet validated cross-domain.

Problem Y (IVN) : Novel-ID flooding and cross-ID fuzzing where per-ID baselines fail.

Component                   Design
Source training             CIC-IDS-2017 — train residual predictor on flow-level features (packet timing, byte rates)
Target adaptation           Map flow residuals to CAN residuals: inter-message timing, DLC consistency, data-byte entropy
Evaluation (novel-ID)       Car-Hacking DoS (ID 0000 flooding) — zero-shot
Evaluation (cross-ID fuzz)  ROAD fuzzing — zero-shot
Control                     Compare against per-ID baseline residualization trained on Car-Hacking normal
Primary metric              F1 on attack classes with novel/blurred IDs


Author-stated support : "Residualization assumes stable per-ID normal baselines and fails when attacks introduce new IDs or blur ID boundaries" (scope, author-stated). Cross-dataset CAN transfer shows statistical features "fail to generalize across attack behaviours" - 6 .

Inference : Flow residuals capture rate-based anomalies that partially transfer to CAN timing anomalies, but the ID-as-anchor problem requires a separate ID-anomaly head (e.g., one-class classifier over ID frequency distribution).

Proposed experiment : 1. Train residual predictor on CIC-IDS-2017 (predict expected inter-packet timing given recent history). 2. Apply to Car-Hacking and ROAD, computing timing residuals per CAN message. 3. Flag messages with residual > threshold. 4. Compare F1 against per-ID baseline method. 5. Report specifically on DoS (novel ID) and fuzzing (cross-ID) subsets.

Split 4: Multi-Stage Binary Decomposition Transfer (IoT-IDS → NIDS)

Method X (IoT-IDS) : Multi-stage deep learning where binary classifiers progressively separate attack categories, as in - 9 (X-IIoTID: 5 stages, 4 binary + 1 multi-class, minority class F1 improved from ~88% to >99%).

Problem Y (NIDS) : Imbalanced multi-class NIDS where minority attacks (e.g., infrequent exploit variants) are drowned by dominant classes.

Component           Design
Source method       MSDL architecture with binary stage decomposition
Target training     CIC-IDS-2017 — reorganize 14 attack types into progressive binary splits (e.g., benign vs all → DoS vs non-DoS → etc.)
Cross-dataset eval  UNSW-NB15 — zero-shot using shared flow features
Adversarial eval    CIC-DDoS-2019 — test on DDoS variants not seen in CIC-IDS-2017
Baselines           Single-stage multi-class classifier (RF, XGBoost)
Primary metric      Minority-class F1 (not weighted accuracy)


Author-stated support : "The improved detection rates for C&C and crypto ransom attacks suggest that the MSDL method effectively reduces false positives... misclassifications of C&C attacks decreased from 7.45% to 0%" - 9 . "When trained on UNSW-NB15 and tested on TON_IoT or vice versa, below 40% accuracy" - 28 demonstrates the need for architectural solutions to generalization.

Inference : Binary decomposition helps with intra-dataset class imbalance but does not inherently solve domain shift — cross-dataset performance will depend on whether the binary splits align with shared feature discriminability.

Proposed experiment : 1. Implement MSDL-style staged binary decomposition on CIC-IDS-2017. 2. Compare minority-class F1 against single-stage XGBoost baseline. 3. Zero-shot evaluate on UNSW-NB15 using only features present in both datasets. 4. Test on CIC-DDoS-2019 to measure generalization to unseen DDoS sub-types.

Split 5: Transfer Learning for Fuzzing Detection (NIDS → IVN)

Method X (NIDS) : Fine-tuning a pre-trained model with frozen early layers, as in - 21 where CarHacking-pretrained CNNs were fine-tuned on CIC-IoV-2024, achieving >99.9% accuracy.

Problem Y (IVN) : Cross-ID fuzzing detection where random CAN IDs and random data bytes must be flagged as anomalous without per-ID baselines.

Component                Design
Source pretraining       UNSW-NB15 — train CNN on flow features encoded as 9×9 or 1D vectors
Intermediate adaptation  Car-Hacking — fine-tune on DoS, fuzzy, spoofing with frozen early layers
Target zero-shot         ROAD fuzzing subset — cross-ID, cross-vehicle
Target few-shot          CAN-ML fuzzing subset — 10% labeled fine-tuning
Ablation                 Feature space: raw CAN bytes vs derived features (ID frequency, timing delta)
Primary metric           F1 on fuzzing class + false positive rate on normal CAN


Author-stated support : "Strategy2 fine-tunes pretrained CarHacking models by freezing layers and training new neurons on CIC-IoV-2024" - 21 . ROAD fuzzing is described as injecting "totally random CAN ID and DATA values every 0.5 milliseconds" - 1 .

Inference : Fuzzing detection requires learning a model of normal ID-data co-occurrence — UNSW-NB15 pretraining provides generic anomaly sensitivity but no CAN-specific ID semantics. The frozen-layer approach may transfer timing/entropy features but not ID-boundary features.

Proposed experiment : 1. Pretrain CNN on UNSW-NB15 binary classification. 2. Fine-tune on Car-Hacking with frozen first 3 layers. 3. Evaluate zero-shot on ROAD fuzzing per vehicle. 4. Compare against Car-Hacking-only training (no NIDS pretraining). 5. Measure whether NIDS pretraining improves early-layer feature quality for CAN anomaly detection.
