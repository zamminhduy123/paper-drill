Scope Diagnosis: Transfer Bottlenecks Across IVN, IoT-IDS, NIDS

The core problem across all three scopes is domain shift : models trained on one network environment (in-vehicle CAN bus, IoT/IIoT traffic, enterprise NIDS) fail catastrophically when deployed on another, even when the abstract attack categories (DoS, flooding, fuzzing) appear semantically similar. The search results confirm this gap is pervasive and under-addressed.

IVN-Specific Bottlenecks

* Author-stated : "The ROAD dataset is highly imbalanced... some classes need to be oversampled. For this reason we employed the SMOTE algorithm... to increase the number of samples of each attack to a fixed value of 100,000" - 1 . Cross-dataset CAN evaluation shows "statistical features provided near-random detection performance with ROC-AUC values as low as 0.0088 (Logistic Regression) and 0.0145 (Fuzzy → RPM) when models were trained on one attack type and evaluated on RPM spoofing attacks" - 6 .

* Inference (model's) : The F1=0.02 on HCRL DoS and F1=0.27 on ROAD cross-ID fuzzing likely stem from a fundamental mismatch: CAN ID is treated as a categorical anchor in residualization schemes, but novel-ID flooding renders that anchor null, and cross-ID fuzzing blurs the decision boundary between "unusual ID" and "attack ID."

* Proposed experiment : Train a CAN ID anomaly detector exclusively on Car-Hacking normal traffic (no attack samples), then evaluate zero-shot on ROAD fuzzing and CAN-ML novel-ID attacks. Measure whether per-ID baseline instability predicts false positives.

IoT-IDS Bottlenecks

* Author-stated : "No single architecture dominates, reflecting the diversity of IoT scenarios and operational constraints. Hybrid and attention-based models generally improve detection effectiveness... but these gains often come at the cost of increased computational overhead" - 3 . "Heavy reliance on benchmark datasets with limited cross-dataset or real-time validation" - 3 .

* Inference (model's) : The triple-model stacking with meta-classifier described in the IoT scope is the canonical example of architectural complexity without deployment feasibility — the meta-classifier's latency is unmeasured on constrained hardware, and the architecture assumes stationary feature distributions that do not hold across IIoT verticals.

* Proposed experiment : Distill a multi-stage model trained on CIC-IoT-2023 into a single lightweight classifier, then evaluate transfer to N-BaIoT and TON_IoT with latency profiling on simulated edge constraints.

NIDS Bottlenecks

* Author-stated : "When trained on UNSW-NB15 and tested on TON_IoT or vice versa, below 40% accuracy. These results reveal a significant generalisation gap in intrusion detection" - 28 . "The field's near-universal omission of FPR, latency, and resource consumption metrics... means that benchmark accuracy rankings do not reliably predict production deployment suitability" - 12 .

* Inference (model's) : The NIDS scope's limitation — "no cross-domain or IVN validation; meta-learner interpretability and feature-space transferability unaddressed" — reflects a broader pattern: NIDS methods optimize for tabular flow features from enterprise traffic, which have no structural correspondence to CAN frames or IoT protocol-specific features.

* Proposed experiment : Map NIDS flow features to IoT-flow features via shared statistical moments (packet inter-arrival variance, byte entropy), train on CIC-IDS-2017 , test zero-shot on CIC-IoT-2023 with feature alignment only.

Concrete Research Splits: Method X from Scope A → Problem Y in Scope B

All proposed splits use only the permitted datasets: Car-Hacking, ROAD, CIC-IoV-2024, CAN-ML, N-BaIoT, TON_IoT, CIC-IoT-2023, CIC-IDS-2017, UNSW-NB15, CIC-DDoS-2019.

Split 1: Statistical Flow Feature Transfer (NIDS → IoT-IDS)

Method X (NIDS) : Statistical flow feature extraction + tree-based ensemble (as in - 23 , where DT achieved 96.25% cross-dataset accuracy TON_IoT → WUSTL-IIoT-2021 on 7 shared features).

Problem Y (IoT-IDS) : Cross-vertical IoT attack detection where labeled target data is scarce.

Component                      Design
Source training                TON_IoT — extract statistical flow features (src/dst port, packet counts, byte counts, duration)
Target evaluation (zero-shot)  CIC-IoT-2023 — map shared semantic features, no retraining
Target evaluation (few-shot)   N-BaIoT — fine-tune on 5% labeled target samples
Baselines                      Random Forest, Decision Tree, Logistic Regression trained natively on target
Primary metric                 Macro-F1 on minority attack classes (not accuracy)


Author-stated support : "Tree-based ensemble models such as Bagging and Stacking show strong generalizability across datasets, whereas LGBM appears to struggle with domain shift" - 23 .

Inference : If semantic feature mapping preserves enough discriminative signal for DoS-like attacks, zero-shot F1 > 0.60 is achievable; fuzzing/spoofing attacks will likely fail without temporal features.

Proposed experiment : 1. Extract 7 shared features from TON_IoT and CIC-IoT-2023. 2. Train RF on TON_IoT binary (benign/attack). 3. Evaluate on CIC-IoT-2023 DDoS, DoS, Mirai subsets. 4. Report per-class F1 and confusion between attack types.
